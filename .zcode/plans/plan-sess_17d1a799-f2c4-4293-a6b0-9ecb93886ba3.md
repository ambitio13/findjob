# Subtask 4: Match Decision And Opening Message

## Goal
Make the backend decide whether a BOSS recommended-job JD is worth contacting. Produce a structured match output (`communicate | skip | needs_review`) with score, reasons, risks, missing requirements, and an opening message — persisted as a `GeneratedArtifact` with full provenance. Low confidence and validation errors stop before any browser side effect.

## Design Decisions

### 1. Synchronous model-backed service (not queue-backed)
Following the `jd_analysis_service` pattern rather than the `readiness_service` queue pattern. The match decision is called synchronously from the inspect endpoint — it does NOT need queue infrastructure for MVP. The 6-step orchestration (load_context → build_prompt_context → call_model → validate_model_output → persist_outputs → complete_run) is identical to `jd_analysis_service._execute_jd_analysis`.

### 2. Match decision as a follow-up endpoint, not embedded in inspect
The design says match decision is an internal service step within `BOSSRecommendedJobService`. However, the inspect endpoint already reads JD + upserts job/application. Embedding the model call in the inspect endpoint would make it slow (model latency) and couple JD reading with match scoring. Instead:

- **New endpoint**: `POST /boss/recommended-jobs/{job_id}/match` — takes `resume_version_id`, runs the match decision model, persists the artifact, returns the decision.
- This keeps inspect fast (JD read + upsert only) and lets the user trigger match explicitly (or the frontend triggers it automatically after inspect succeeds).
- The endpoint creates its own `AgentRun` with `workflow_type="boss_match_decision"`.

### 3. Output field names
Use the design.md contract exactly: `decision`, `score` (float 0.0–1.0), `reasons` (list[str]), `risks` (list[str]), `missing_requirements` (list[str]), `opening_message` (str | None — None when decision ≠ communicate).

The PRD calls it `recommended_opening_message` but design.md calls it `opening_message`. Design.md is the authoritative contract, so we use `opening_message`. The API response schema will alias it for backward clarity.

### 4. Opening message validation (net-new)
The acceptance criteria require "Opening message length/tone/PII rules are validated." Since no existing code does this, we add a post-validation sanitizer:

- **Length**: 10–500 characters (Chinese-aware; rejects empty/too-short/too-long)
- **PII redaction**: reject if contains phone numbers (11-digit patterns), email addresses, or ID-card-like patterns — the opening message should contain NO personal contact info (it goes to a recruiter who doesn't need it yet)
- **Tone**: reject if contains profanity markers or excessive punctuation (basic check)
- On validation failure: the `decision` is downgraded to `needs_review` (NOT `communicate`), and the `opening_message` is set to `None`. This satisfies "Invalid model JSON never becomes a communicate decision" and "Opening message length/tone/PII rules are validated."

### 5. Score-based gating
The PRD says "低置信度、关键字段缺失、明显不匹配、薪资/城市/经验不符合时，不允许自动沟通." We implement this as a post-model safety gate:
- If `decision == "communicate"` but `score < 0.6` → downgrade to `needs_review` (low confidence)
- If `decision == "communicate"` but `missing_requirements` is non-empty → downgrade to `needs_review`
- This is a deterministic backend rule, NOT delegated to the model.

### 6. Provenance and artifact persistence
- `GeneratedArtifact(artifact_type="boss_match_decision", content=validated_output.model_dump_json(), ...)`
- `source_ids` dict: `user_id, job_id, resume_id, resume_version_id, application_id (if linked), model_request_id, provider, model, prompt_version, workflow_type, usage`
- No raw JD/resume text in `source_ids` (same rule as jd_analysis).

### 1. NEW: `backend/app/schemas/boss_match_decision.py`
Pydantic schemas for the match decision workflow:

```python
class MatchDecision(StrEnum):
    communicate = "communicate"
    skip = "skip"
    needs_review = "needs_review"

class MatchDecisionModelOutput(BaseModel):
    """Persistence gate — validated structured output from the model."""
    decision: MatchDecision
    score: float = Field(ge=0.0, le=1.0)
    reasons: list[str] = Field(default_factory=list)
    risks: list[str] = Field(default_factory=list)
    missing_requirements: list[str] = Field(default_factory=list)
    opening_message: str | None = None

class MatchJobRequest(BaseModel):
    """Body of POST /boss/recommended-jobs/{job_id}/match."""
    resume_version_id: str = Field(min_length=1)

class MatchDecisionOut(BaseSchema):
    """Response for the match endpoint."""
    decision: MatchDecision
    score: float
    reasons: list[str]
    risks: list[str]
    missing_requirements: list[str]
    opening_message: str | None
    job_id: str
    agent_run_id: str | None = None
    artifact_id: str | None = None
    message: str | None = None  # human-readable explanation (e.g. "low confidence, downgraded to needs_review")
```

## Safety Invariants Preserved
- **"Low confidence and validation errors stop before browser side effects"** — the safety gate downgrades low-score/missing-requirements/invalid-opening-message decisions from `communicate` to `needs_review`. No browser action is triggered.
- **"Invalid model JSON never becomes a communicate decision"** — JSON parse failure raises `BossMatchValidationError` → run fails → 502 → no artifact persisted.
- **"Opening message length/tone/PII rules are validated"** — `validate_opening_message()` checks length (10–500), PII (phone/email/id-card regex), and tone. Invalid messages downgrade the decision to `needs_review`.
- **"Fake provider tests cover communicate/skip/needs_review"** — three fake outputs in `_BOSS_MATCH_FAKE_OUTPUTS`.
- Cross-user access returns 404 (not 403).
- No raw JD/resume text in `source_ids` provenance.
- One job_id per match call — no batch paths.
- The match decision endpoint does NOT trigger any browser action — it only produces a decision + opening message. Browser side effects come later in Subtask 6.
