# Subtask 5: Communication Action Draft, Approval And Idempotency

## Goal
When the match decision returns `communicate`, prepare a side-effect `boss_immediate_communicate` action carrying the exact opening message, bind it with `payload_hash` + external idempotency key, require approval, and make stale source/payload invalidate approval. This subtask delivers the **prepare/draft + execute-gate** — the actual browser side effect is Subtask 6, so the execute endpoint will run all guards but stop before the adapter call (returning a "guarded but not yet executed" result).

## Design Decisions

### 1. New action type `boss_immediate_communicate` in `ExternalActionType`
Add `boss_immediate_communicate = "boss_immediate_communicate"` to the existing `ExternalActionType(StrEnum)` enum in `application_action.py`. This is distinct from the existing `hr_message` because the design contract explicitly names this action type and its lifecycle is BOSS-specific (click + send opening message, not a form submit).

### 2. Idempotency key shape — reuse the existing `{application_id}:{action_type}:{payload_hash}`
The design.md says `boss:communicate:<user_id>:<job_url_hash>:<resume_version_id>:<payload_hash>`, but the codebase already has a proven, tested idempotency key system via `compute_external_idempotency_key(application_id, action_type, payload_hash)` → `f"{application_id}:{action_type.value}:{payload_hash}"`. This already encodes application (which binds user + job + resume_version) and the exact payload. We **reuse the existing shape** rather than inventing a parallel one — the `job_url_hash` is already bound via the application → job → `external_id` chain, and `user_id` is bound via the application's `user_id`. This satisfies the PRD R3 uniqueness rule (`platform + user + job_url_hash + resume_version + payload_hash`) because each `application_id` is unique per (user, job, resume_version).

### 3. Synchronous prepare (no queue worker)
Unlike `platform_submit` (which uses a queue worker for the prepare phase because it drives a browser dry-run fill), the BOSS communicate prepare is **purely synchronous**: it reads the match decision artifact, extracts the opening message, builds the `ApplicationActionPreview`, computes `payload_hash` + idempotency key, and persists the action — all in the request. No browser interaction, no queue. This mirrors `approval_action_service.preview_action` (which is synchronous).

### 4. Prepare creates the action in `approval_required` status (not `draft`)
Following the existing `approval_action_service.preview_action` pattern: the action is created directly in `approval_required` status. The design.md lists `draft` as a status but the existing infrastructure starts at `approval_required` — we follow the existing pattern.

### 5. Store `decision_trace` + `job_url_hash` in `source_snapshot` JSON
The `ApplicationActionSourceSnapshot` has fixed fields (`job_id, resume_version_id, artifact_ids, source_hash`). We store `decision_trace` and `job_url_hash` as extra keys in the `source_snapshot` JSON column (which is a flexible JSON dict). The `source_hash` is computed from the current job/resume/profile metadata (reusing `build_source_snapshot`), so source staleness is detected by `assert_action_approved` exactly as in the platform_submit flow.

### 6. Execute endpoint mirrors `run_platform_guided_submit_submit` but stops before adapter
The execute endpoint runs the full guard chain (idempotency key check → recompute payload hash → recompute source hash → `assert_action_approved`), but since Subtask 6 delivers the actual browser adapter method, the execute endpoint in this subtask will:
- Run all guards
- Record `external_started_at`
- Append `boss_communicate_started` timeline event
- **Return a 200 with the guarded action** (not call any adapter yet)

This gives us a fully testable approval/idempotency gate now, and Subtask 6 will swap in the adapter call. The endpoint is named `POST /boss/recommended-jobs/{job_id}/communicate/execute` and takes the `action_id` in the request body.

Actually, re-reading the patterns more carefully: the platform_submit execute uses `run_id` in the path because it ties to a prepare run. For communicate, the prepare is synchronous (no run), so the execute endpoint should take `action_id` directly. We use `POST /applications/{application_id}/boss-communications/{action_id}/execute`.

### 7. Source hash for communicate = readiness source hash (same as platform_submit)
Reuse `build_source_snapshot` + `compute_source_hash` from `application_state.py` with the same `_PROMPT_VERSIONS = {"readiness": "pilot"}`. The source hash covers job_id, job_updated_at, resume_version_id, resume_version_no, profile_updated_at, prompt_versions — if any of these change after the action is approved, `assert_action_approved` detects the staleness.

### 3. NEW: `backend/app/services/boss_communicate_service.py`
Service module with:

- `WORKFLOW_TYPE = "boss_communicate"` (for AgentRun if needed; prepare is synchronous so no run created)
- `prepare_communicate_action(db, current_user, job_id, resume_version_id, match_artifact_id) -> ApplicationAction`

  - Parse artifact content (JSON) → `MatchDecisionModelOutput`
  - Assert `decision == "communicate"` (422 if not — can't prepare a communicate action from a skip/needs_review decision)
  - Assert `opening_message` is not None (422 — safety gate should have cleared it, but defensive)
  - Re-validate the opening message via `validate_opening_message` (422 if now invalid)
  - Build `ApplicationActionPreview(action_type=boss_immediate_communicate, target_platform="boss", target_resource=job.id, selected_artifact_ids=[match_artifact_id], outgoing_text=opening_message, resume_file_reference=resume_version_id)`
  - Compute `payload_hash = compute_payload_hash(preview)`
  - Compute `idempotency_key = compute_external_idempotency_key(application_id=record.id, action_type=ExternalActionType.boss_immediate_communicate, payload_hash=payload_hash)`
  - Compute `source_hash` via `build_source_snapshot` (reuse the platform_submission pattern)
  - Build `source_snapshot` dict with `job_id, resume_version_id, artifact_ids=[match_artifact_id], source_hash` + extra keys `job_url_hash` (from `job.external_id`) and `decision_trace` (the full match decision output minus opening_message)
  - Check for existing non-terminal `boss_immediate_communicate` action for this application — reuse it (refresh in place) like `_find_active_platform_submit_action`
  - Create/update the action in `approval_required` status
  - Append `boss_communicate_previewed` timeline event (no status change on the application)
  - Commit + return action

- `load_communicate_execute_context(db, current_user, application_id, action_id) -> tuple[ApplicationRecord, AgentRun | None, ApplicationAction]`
  - Load application (404 cross-user)
  - Load action via `get_for_user_and_application` (404)
  - Assert `action.action_type == "boss_immediate_communicate"` (404)
  - Return `(record, None, action)` — no run needed for communicate

- `class BossCommunicateBlockedError(Exception)` — mirrors `PlatformSubmitBlockedError` with `reason, message, action_id`

- `async def run_boss_communicate_execute(db, *, current_user, application_id, action_id) -> tuple[ApplicationRecord, ApplicationAction]`
  - Mirror `run_platform_guided_submit_submit` guard chain:
    1. Load context
    2. Guard 0: idempotency key check — if terminal result exists, return existing action (append `boss_communicate_blocked` timeline with `reason="idempotency_replay"`)
    3. Recompute `current_payload_hash` from stored preview
    4. Recompute `current_source_hash` from current job/resume/profile
    5. Guard 1: `assert_action_approved(action, current_payload_hash=, current_source_hash=)` → catch `ApprovalBlockedError` → re-raise as `BossCommunicateBlockedError`
    6. Record `external_started_at` + flush
    7. Append `boss_communicate_started` timeline event
    8. **Subtask 5 stops here** — return `(record, action)` with a message "guards passed". Subtask 6 will insert the adapter call after step 7.

Let me reconsider: the execute endpoint should be under `/applications/{application_id}/boss-communications/{action_id}/execute` to match the approval_actions pattern (`/applications/{application_id}/actions/...`). But the prepare endpoint is under `/boss/recommended-jobs/{job_id}/communicate/prepare` because it starts from the job (before an application might exist... actually the application is created during inspect).

- `POST /boss/recommended-jobs/{job_id}/communicate/prepare` — takes `resume_version_id` + `match_artifact_id`, creates the action, returns it

This keeps the communicate flow rooted at the job level, consistent with the match endpoint. The `application_id` is needed for the execute because the action is scoped to an application.

Actually, simpler: the action already has `application_id` on it. The execute endpoint can look up the action by `action_id` + `job_id` (via the action's `target_resource` = job_id) + user. No need for `application_id` in the body. Let me use:

- `POST /boss/recommended-jobs/{job_id}/communicate/{action_id}/execute` — no body needed, looks up action by action_id, verifies `target_resource == job_id`, runs guards.

## Safety Invariants Preserved
- **"Unapproved execute returns 409/approval-required"** — `assert_action_approved` raises `ApprovalBlockedError` → `BossCommunicateBlockedError` → HTTP 409.
- **"Same idempotency key cannot send twice"** — Guard 0 checks `get_terminal_for_idempotency_key` and short-circuits.
- **"Payload changes require reapproval"** — `current_payload_hash != approval.approved_payload_hash` → `payload_hash_mismatch` block.
- **"Stale source/payload invalidates approval"** — `current_source_hash != action.source_snapshot.source_hash` → `source_stale` block.
- **"Timeline records draft, approval, running and terminal states"** — `boss_communicate_previewed` (prepare), existing `action_approved` (approve), `boss_communicate_started` (execute start), `boss_communicate_blocked` (idempotency replay). Terminal result timeline events come in Subtask 6.
- **Cross-user access returns 404 (not 403).**
- **No raw JD/resume text in persisted rows** — only IDs + hashes + opening message (which is the exact payload being approved).
- **One application_id per call — no batch paths.**
- **"Invalid model JSON never becomes a communicate decision"** — prepare requires an existing `boss_match_decision` artifact with `decision == "communicate"`; if the match failed, no artifact exists to prepare from.
