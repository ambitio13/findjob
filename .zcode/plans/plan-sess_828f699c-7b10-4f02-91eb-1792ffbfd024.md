## Fix 1: JD 粘贴异步化（弹窗不再阻塞等待）

### 问题
当前 `JobCreateModal` 两阶段阻塞流程：粘贴 JD → 点击"智能解析" → **弹窗保持打开**轮询 AgentRun → 解析完成后显示可编辑字段 → 手动保存创建 JobPosting。用户体验：弹窗一直占着屏幕，没有异步感。

### 根因
`POST /jobs/parse` 创建 AgentRun 时**不创建 JobPosting**（parse-then-create 设计），worker 把解析结果写入 `AgentRun.result.fields`，前端必须在弹窗内轮询完才能拿到结果去创建 job。

### 方案：改为 create-job-first 模式

**后端改动：**

1. **`backend/app/api/v1/jobs.py` — `POST /jobs/parse`（行 93-159）**
   - 在创建 AgentRun 之前，先用 `job_repo.create()` 创建一个 JobPosting：
     - `company="(解析中…)"`, `title="(解析中…)"` 作为占位符
     - `jd_raw=payload.raw_jd`
     - `platform=payload.platform or "manual"`
     - `jd_normalized=None`
   - 创建 AgentRun 时传入 `job_id=job.id`（把 run 关联到 job 行）
   - 响应改为返回 `JobOut`（含 job 信息）+ `run` 摘要，而不是只返回 run + raw_jd
   - 新增响应 schema `JdParseSubmitResponse` 增加 `job: JobOut` 字段

2. **`backend/app/queue/payloads.py` — `JdPasteParsePayload`（行 74-90）**
   - 增加 `job_id: str` 字段（worker 需要知道回写到哪个 job）
   - 保留 `raw_jd`（worker 仍从 payload 读 raw_jd，不从 DB 读，保持队列隔离原则）

3. **`backend/app/services/jd_parse_service.py` — `parse_jd_with_run`（行 278-326）**
   - Step 5（persist_outputs）：成功时把解析结果写回 `JobPosting.jd_normalized`
   - 增加可选参数 `job_id: str | None`，传入时在 step 5 中 `db.get(JobPosting, job_id)` 并设置 `job.jd_normalized = {"_extraction": ..., "fields": ...}`
   - 同时更新占位符 company/title：如果 `output.company` / `output.title` 非空，用解析值覆盖占位符

4. **`backend/app/queue/handlers.py` — `jd_paste_parsing`（行 156-163）**
   - 把 `payload.job_id` 传给 `parse_jd_with_run`

5. **`backend/app/api/v1/jobs.py` — `POST /jobs/{job_id}`（行 51-71）**
   - 新增 `PATCH /jobs/{job_id}` 端点：允许用户编辑 company/title/location/salary_range/direction/platform/jd_raw
   - `job_repo` 新增 `update()` 函数

**前端改动：**

6. **`frontend/src/features/jobs/JobCreateModal.tsx`（整体重写交互流程）**
   - 点击"智能解析"后：调用 `parseJobJd` → 拿到 `job` → 调用 `onCreated(job)` → **立即关闭弹窗**
   - 弹窗只保留 JD 粘贴 + "智能解析" + "跳过解析手动填写"两个入口
   - 手动填写模式：保持现有两阶段流程（手动填表 → 保存创建 job）

7. **`frontend/src/features/jobs/JobsTable.tsx`（行 16-43）**
   - 新增"解析状态"列：读取 `job.jd_normalized` 是否为 null 判断
   - 对刚创建的占位符 job（company/title 为 "(解析中…)"），用 `listAgentRuns(jobId, "jd_paste_parsing")` 轮询
   - 新增 polling：对有活跃 parse run 的 job，每 3s 刷新列表

8. **`frontend/src/pages/jobs/JobDetailPage.tsx`**
   - 顶部"职位详情"卡片增加编辑按钮：点击后展开内联编辑表单（company/title/location 等），调用 `PATCH /jobs/{id}`
   - 如果 job 的 company/title 仍是占位符且 parse run 已完成，提示用户编辑

9. **`frontend/src/api/client.ts` + `frontend/src/types/index.ts`**
   - `parseJobJd` 返回类型更新（增加 job 字段）
   - 新增 `updateJob(id, payload)` 函数 + `JobUpdate` 类型

### 测试更新
- `test_jd_parse_api.py`：断言 `POST /jobs/parse` 同时创建了 JobPosting（company/title 占位符），AgentRun 关联 job_id
- 新增 `test_update_job`：PATCH 端点测试
- Worker 测试：断言成功解析后 `job.jd_normalized` 被写入、占位符被覆盖

## Fix 2: JD 分析初始状态显示"失败"（纯前端修复）

### 问题
`JobDetailPage.tsx` 的 `AnalysisSection` 中，queued/running 状态的 run（还没有 JobAnalysis detail）被显示为"运行失败"。

### 根因
`JobDetailPage.tsx:532`：
```typescript
const isFailed = v.run.status === "failed" || !v.detail;
```
`!v.detail` 对 queued/running 的 run 返回 true（此时还没产出 JobAnalysis 行），导致 label 显示"运行失败"，下方显示"该次运行未产出有效结果"警告。

### 方案（纯前端）

**`frontend/src/pages/jobs/JobDetailPage.tsx`（行 531-559）**

1. 修改 Select options 的 label 逻辑：
   ```typescript
   const isFailed = v.run.status === "failed";
   const isPending = ACTIVE_AGENT_RUN_STATUSES.has(v.run.status as AgentRunStatus);
   const label = v.detail?.structured
     ? RECOMMENDATION_LABEL[v.detail.structured.recommendation] ?? v.detail.structured.recommendation
     : isFailed ? "运行失败"
     : isPending ? "运行中"
     : "无结果";
   ```

2. 修改选中 run 的内容渲染（行 545-559）：
   - `selected.detail` 存在 → 显示 `<AnalysisResult>`（现有逻辑）
   - run 是 queued/running → 显示"分析运行中…"Alert + `<AgentRunStatusTag status={selected.run.status} />`（复用 `ArtifactChecklist` 的模式）
   - run 是 failed 且无 detail → 显示现有的"该次运行未产出有效结果"警告

3. 引入 `ACTIVE_AGENT_RUN_STATUSES` 和 `AgentRunStatusTag`（文件已 import `ACTIVE_AGENT_RUN_STATUSES`，需补 import `AgentRunStatusTag`）

### 测试
- 前端 lint + type-check + build 确保无类型错误

## Fix 3: 创建投递记录自动生成 4 个就绪材料

### 问题
创建投递记录后，用户需要手动逐个点击生成 4 种就绪材料（HR 开场话术、简历改写片段、技能差距计划、面试准备），体验繁琐。

### 方案：创建后自动并行触发 4 个生成

**关键约束：**
- 仅在**新创建**的记录上自动触发（重复创建返回已有记录时不触发，避免重复生成）
- 需要 `resume_version_id`（未绑定简历的记录跳过自动生成）
- 后端 409 duplicate-active-run guard 已存在，自动触发时前端静默吞掉 409
- `ArtifactChecklist` 当前只追踪单个 `pollRunId`，需改为追踪多个并发 run

**后端改动：**

1. **`backend/app/schemas/api.py` — `ApplicationOut`（行 146-159）**
   - 增加 `is_duplicate: bool = False` 字段，让前端区分新建 vs 重复

2. **`backend/app/api/v1/applications.py` — `create_application`（行 97-116）**
   - `application_service.create_application` 返回 `(record, is_new)` 元组
   - 响应中设置 `is_duplicate`

3. **`backend/app/services/application_service.py` — `create_application`（行 93-156）**
   - 返回类型改为 `tuple[ApplicationRecord, bool]`（record, is_new）
   - 重复路径返回 `(existing, False)`，新建路径返回 `(record, True)`

**前端改动：**

4. **`frontend/src/features/applications/ArtifactChecklist.tsx`（重构轮询逻辑）**
   - 新增 prop `autoGenerate: boolean`（首次挂载且为 true 时触发自动生成）
   - 把单 `pollRunId` 改为 `pollRunIds: Map<ReadinessArtifactType, string>`（追踪多个并发 run）
   - 新增 `handleGenerateAll()`：并行调用 4 次 `generateReadinessArtifact`，静默吞掉 409
   - 对每个成功的 enqueue 注册一个 `useAgentRunPolling`（或用一个轮询循环轮询所有活跃 run）
   - 生成中 Alert 显示每个 type 的进度状态

5. **`frontend/src/pages/applications/ApplicationsPage.tsx` / `JobDetailPage.tsx`**
   - `handleCreateApplication` 成功后，传递 `autoGenerate` 标记到 `ApplicationDetail` → `ArtifactChecklist`
   - 或：`ArtifactChecklist` 通过 URL state / localStorage 获取"刚创建"标记

**实现选择（简化方案）：**
- `ArtifactChecklist` 挂载时检查 `application.status === "planned"` 且 `artifacts.length === 0` 且 `!resumeMissing` 且未曾自动触发过（用 `useRef` 去重）→ 自动调用 `handleGenerateAll()`
- 这样不需要后端 `is_duplicate` 字段，因为重复创建的记录要么已有 artifacts、要么 status 不再是 planned

6. **`frontend/src/api/client.ts`**
   - 不需要新增函数（复用 `generateReadinessArtifact`）

### 测试更新
- `test_applications_api.py`：断言 `create_application` 返回 `is_duplicate` 字段
- 前端：lint + type-check + build
