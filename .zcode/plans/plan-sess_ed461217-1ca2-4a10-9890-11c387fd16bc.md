# BOSS 自动沟通 Agent 发展规划

## 总体路线

```
阶段 A (可用)  → 前端 PilotPanel + 半自动 loop（inspect→match→prepare 串行，execute 人工确认）
阶段 B (可靠)  → 选择器后端下发 + 漂移检测（消除 B1 类 bug 根因）
阶段 C (积累)  → 用半自动 loop 积累 10 次 dry-run 无事故
阶段 D (规模)  → 打开 auto-execute → 推荐列表全自动大循环
阶段 E (兜底)  → CDP fallback（最低优先级）
```

对应现有 6 个 trellis 子任务，**不新建任务**，而是更新各子任务 PRD 以体现"半自动 loop"这条主线。

### A3. RecommendedJobPilotPanel 组件

**文件**: `frontend/src/features/applications/RecommendedJobPilotPanel.tsx`

以 `GuidedSubmitPanel.tsx` 为模板（同为 Card + 两阶段审批门控 + bridge 状态），但流程不同：

```
┌─────────────────────────────────────────────┐
│ BOSS 推荐职位引导沟通                          │
├─────────────────────────────────────────────┤
│ [Bridge 状态]  已连接 · page_id: abc123       │
│                心跳: 3s前                      │
├─────────────────────────────────────────────┤
│ 步骤 1: 读取当前职位                           │
│   [开始读取] → 显示 JD 预览（标题/公司/薪资/描述）│
├─────────────────────────────────────────────┤
│ 步骤 2: 匹配决策                               │
│   [匹配分析] → 决策: communicate (score: 0.82) │
│   理由: ...  风险: ...                         │
│   开场白: "您好，看到贵司..." [可编辑]           │
├─────────────────────────────────────────────┤
│ 步骤 3: 准备                                   │
│   [准备发送] → action 已创建 (approval_required)│
├─────────────────────────────────────────────┤
│ 步骤 4: 人工审批                               │
│   [批准] / [撤销]                              │
├─────────────────────────────────────────────┤
│ 步骤 5: 执行发送                               │
│   [执行] → 终态: succeeded / duplicate / unknown│
└─────────────────────────────────────────────┘
```

**关键设计决策**：

1. **手动模式（默认）**: 每步都需要用户点击按钮触发。这是当前安全不变量的直接前端化。

2. **半自动 loop 模式（开关）**: 面板顶部一个 Switch「半自动模式」。开启后：
   - 步骤 1→2→3 **自动串行执行**（inspect 成功后自动 match，match 返回 communicate 后自动 prepare）
   - 步骤 3 完成后 **停在 approval_required**，等待人工批准
   - 批准后 **停在 execute 前**，等待人工点击执行
   - 任何步骤失败/返回 skip/needs_review → 自动停止，显示原因

3. **安全不变量保持**: 半自动 loop 只自动化 inspect→match→prepare（均为只读/无副作用操作），execute 仍需人工确认。**不违反**"prepare never clicks final submit"和"execute needs approval"两条不变量。

4. **状态管理**: 组件内 `useState` 管理当前步骤、inspect 结果、match 结果、action 状态。不需要全局状态——这是单面板的线性流程。

5. **复用现有 hook**: `useBridgeStatus()` 直接复用（5s 轮询，已验证可用）。

## 阶段 B: 选择器后端下发 + 漂移检测

### B1. 选择器后端下发

**任务**: `08-03-boss-userscript-selector-backend-dispatch` (P2-2)

**问题**: userscript 中 3 处硬编码选择器与 `selectors.py` 漂移（B1 根因）：

| 位置 | 硬编码内容 | 后端常量 |
|------|-----------|---------|
| `read_communication_result` success marker (user.js:658) | 5 条 CSS 选择器 | `COMMUNICATION_SUCCESS_MARKER` |
| `read_communication_result` duplicate marker (user.js:661) | 4 条 CSS 选择器 | `COMMUNICATION_DUPLICATE_MARKER` |
| `read_communication_result` error marker (user.js:668) | 3 条 CSS 选择器 | `PLATFORM_ERROR_MARKER` |
| `send_opening_message` textarea (user.js:605) | 4 条 CSS（子集） | `COMMUNICATION_MESSAGE_INPUT`（更宽） |

**方案**: 扩展 `Instruction` 数据结构，新增 `extra_selectors` 字段：

```python
# userscript_channel.py - Instruction dataclass 新增
extra_selectors: dict[str, str] | None = None
# key = marker name ("success" / "duplicate" / "error" / "message_input")
# value = CSS selector string
```

- `make_instruction()` 新增 `extra_selectors` 参数
- `InstructionOut` schema 新增对应字段
- `read_communication_result` 的 `make_instruction()` 调用改为携带 3 组选择器（从 `selectors.py` 读取常量值）
- `send_opening_message` 的 Enter-key 路径改用 `extra_selectors["message_input"]`（或复用 `selector_value` 字段传 `COMMUNICATION_MESSAGE_INPUT`）
- userscript `read_communication_result` handler 改为从 `ins.extra_selectors` 读取，移除硬编码
- userscript `send_opening_message` Enter-key 路径改为从 `ins.selector_value` 或 `ins.extra_selectors` 读取

**向后兼容**: 旧版 userscript（不读取 `extra_selectors`）会 fallback 到硬编码——加一个 `userscript_version` 心跳字段检测，不匹配时前端提示更新。

**额外漂移点**: `extractBossRecommendedJobV1`（user.js:175-265）有 10 个 JD 提取选择器完全在 userscript 侧，后端无对应常量。这属于 P2-2 范围但工作量大，**本期暂不处理**，在 PRD 中标注为后续工作。

### B2. 选择器漂移自动检测

**任务**: `08-03-boss-selector-drift-detection` (P2-4)

**方案**: 在 communicate `prepare` 阶段（`boss_communicate_service.py`）插入漂移检测步骤：

- 定义关键选择器清单：`IMMEDIATE_COMMUNICATE_BUTTON`, `COMMUNICATION_MESSAGE_INPUT`, `COMMUNICATION_SEND_BUTTON`
- 通过 userscript bridge 发送 `probe_elements` 指令（OpKind 已存在），检查关键选择器是否可见
- 任何关键选择器不可见 → 返回 `selector_drift`（而非 `unknown`），`diagnostic_reference` 标注具体选择器名
- 只读检查，不增加任何点击/填充，不影响安全不变量

**依赖**: 建议在 B1 完成后实施（后端可控选择器列表后，漂移检测更精确），但也可独立先行。

## 阶段 C: Dry-run 门槛积累

**任务**: `08-03-boss-dry-run-gate` (P3-4)

这是手动验证任务，无代码产出。**关键改变**: 不再依赖 curl 手动操作，而是用阶段 A 的半自动 loop 面板来积累：

- 每次用半自动 loop 执行 inspect→match→prepare（自动），人工审阅后 execute
- 每次 execute 后记录到 `check.jsonl`：日期、脱敏 URL、`read_communication_result` 返回值、`external_result_status`、异常情况、对账结论
- 连续 10 次无事故（0 wrong-tab / 0 duplicate 误发 / 0 unexpected unknown）→ 通过门槛
- 至少 2 次 `duplicate_detected` 场景
- 出现事故 → 计数归零

**依赖**: 阶段 A 完成后开始。

## 阶段 D: 推荐列表全自动大循环

**任务**: `08-03-boss-recommended-list-batch-loop` (P3-2)

**方案**: 后端新增批量编排端点 + 前端扩展 PilotPanel：

1. **后端**: 新增 `POST /boss/recommended-jobs/batch-loop` 端点
   - 串行遍历推荐列表（受"单活跃 application"不变量约束）
   - 每个职位：inspect → match → prepare → **auto-approve**（门槛通过后启用）→ execute
   - 连续 N 次失败触发硬停止
   - 返回 batch run id，前端轮询进度

2. **前端**: PilotPanel 扩展「批量模式」标签页
   - 显示推荐列表 + 每个职位处理状态
   - 进度条（当前 N/总数）
   - 暂停/恢复按钮
   - 每个职位结果独立显示

3. **安全门控**: `auto-execute` 开关默认关闭，只有 dry-run 门槛通过后才能开启。开关状态持久化在后端配置中。

**依赖**: 阶段 C（10 次 dry-run 通过）是硬前置。

## 阶段 E: CDP fallback

**任务**: `08-03-boss-real-adapter-communicate-fallback` (P3-3)

**最低优先级**。在 `RealBossAdapter` 中实现 `execute_communication()`：
- 用 Playwright `BossPage` 执行 communicate 流程

## 风险与约束

- **安全不变量**: 半自动 loop 只自动化只读步骤（inspect/match/prepare），execute 始终需要人工确认。后端"no batch paths"不变量不受影响——前端 loop 本质是串行调用单职位端点。
- **Docker 镜像固定**: 若阶段 B 需要后端改动，需要 `docker compose build backend` + `docker compose up -d backend`。
- **背景 tab 节流**: 已通过 120s/90s 超时缓解，半自动 loop 在前台 tab 运行无影响。
- **选择器漂移**: JD 提取选择器（10 个）仍完全在 userscript 侧，本期不处理，在 PRD 中标注为已知技术债。
